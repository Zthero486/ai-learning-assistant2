## 三、协作流程（可查痕迹）

```
master ← PR ← develop ← PR ← feat/xxx（各自分支）
                  ↑
              issue 驱动
```

1. **需求/缺陷先开 issue**（模板见 `.github/ISSUE_TEMPLATE/`），确认后再动手；
2. 从 `develop` 切功能分支，命名 `feat/<模块>-<简述>`（如 `feat/frontend-dashboard-chart`）；
3. 提交遵循 Conventional Commits，**一次提交只做一件事**；
4. 推送后发 PR 到 `develop`，由**另一名成员** review 后合入（互为 reviewer，避免自审）；
5. commit 信息或 PR 描述关联 issue 编号（`Closes #12`）。

**归属规则**：谁的模块谁提交，跨模块改动在 PR 中说明并由对方 review——这样每个成员的提交记录与 issue/PR 记录都真实反映其工作量。

## 四、工作量度量方法

度量以 **git 仓库客观数据**为准（不使用人工填报），脚本化、可复核：

```bash
python scripts/count_lines.py --write   # 生成 docs/工作量统计.md
```

产出三类指标：

| 指标 | 数据来源 | 用途 |
| --- | --- | --- |
| 新增/删除代码行、涉及文件数、提交数 | `git log --numstat` 按作者聚合 | 代码工作量主体 |
| 模块分布（后端/前端/文档/脚本/CI） | 按路径归类 | 验证分工与角色一致 |
| issue 数、PR 数、review 次数 | GitHub 仓库页面 | 设计与测试类工作的可见产出 |

统计时**排除**依赖（`node_modules`）、构建产物（`dist`）、锁文件与运行数据（`data/`），避免虚增。当前实测数据见 `docs/工作量统计.md`（每次迭代后重跑刷新）。

## 五、绩效分配方式与原因

**分配公式**（总分 100%）：

| 维度 | 权重 | 度量依据 |
| --- | ---: | --- |
| 代码贡献 | 40% | `count_lines.py` 统计的两人有效新增行占比（含难度系数修正） |
| 文档与测试 | 30% | 文档篇幅/图表数、测试用例数与覆盖率提升 |
| 协作痕迹 | 20% | issue 提出与关闭数、PR 数与 review 参与次数 |
| 演示与答辩 | 10% | 演示视频质量、答辩讲解负责模块的清晰度 |

**难度修正**：架构重构、RAG 检索、AI 引擎等属于高复杂度模块，按 ×1.2 系数计入；纯样式调整按 ×0.8 计。修正仅在两人之间做**相对比较**，不改变总权重。

**为什么这样分**：评分表明确指出"多人团队只一人提交代码仓库""测试、设计人员缺乏工作量展示"是扣分项，因此本项目刻意让**每人都有代码 + 文档/测试 + issue/PR 三类可见产出**；同时用权重把"写代码"与"做设计文档、测试、答辩"放在同一评价体系里，避免出现"只有写代码的人得分"的偏差。实际分配比例在结课前依据 `docs/工作量统计.md` 的最终数据核算，并在文档中公开计算过程，保证可核对。
