# 前后端说明（简版）

> 面向演示与快速理解：前端讲功能板块，后端讲 AI 框架、模块协作与状态机。细节见《用户手册》《信息安全设计》。

## 一、前端：功能板块

前端是 Vue 3 + Element Plus 单页应用，13 个页面按学习闭环组织：

| 页面 | 板块 | 在闭环里的位置 |
|---|---|---|
| Login / ChooseTrack | 登录、选课 | **先选课再学**：一个账号只学一门，界面全部围绕该课程展开 |
| Dashboard | 学习看板 | 进度总览、今日待办的入口 |
| Syllabus | 教材目录 | 四史 32 章 193 节骨架 + 章节正文阅读（字号可调、AI 划线高亮） |
| Timeline | 四史时间轴 | 四条历史线索对照浏览 |
| Materials | 史料笔记 | 上传资料、笔记管理 |
| KnowledgePoints | 知识点 | 按章节/朝代组织知识点卡片 |
| Practice | 自测 | AI 出题、单选按钮作答、即时判分 |
| WrongBook | 错题本 | FSRS 间隔复习排期、AI 错因诊断 |
| Tasks | 复习任务 | AI 排的计划在这里逐条打卡 |
| AiAssistant / AiChat | AI 助手 | 全屏对话页；`AiFloat` 浮窗全局挂载，任何页面可呼出 |
| Sync | 同步备份 | 多机数据按 uuid 合并 |

页面间靠「跳转联动」串成闭环：AI 出题附教材原文依据 → 点击跳到 Syllabus 对应章节并高亮原文（`?hl=` 参数）；错题诊断跳转 AI 助手并自动发问（`?q=` 参数）。

## 二、后端：AI 框架的搭建

后端是 FastAPI + 裸 sqlite3（无 ORM）单体，按能力切成 8 个模块（`backend/app/`）：

```
main.py      路由 + 建表迁移 + 业务逻辑（59 个接口）
ai_agent.py  AI 智能体：状态机 + 26 个工具
ai_helper.py AI 通道适配：多平台接入、主备故障转移、规则引擎降级
auth.py      PBKDF2 口令哈希 + HMAC 令牌
srs.py       FSRS 间隔复习适配层
sync.py      uuid 键控多机同步
qushi.py     四史章节骨架 + 教材正文
apppaths.py  开发态/打包态路径解析
```

### AI 框架三层结构

1. **通道层（ai_helper）**——把不同大模型平台（阶跃、智谱等，都是 OpenAI 兼容协议）统一成一套调用接口。主通道超时/限流/5xx 时**自动切备用**（实测 1.17 秒完成，用户无感）；完全没配 key 时降级为**规则引擎**（关键词检索 + 模板作答），软件不瘫痪。
2. **智能体层（ai_agent）**——大模型只会「说」，要让它「做」，就给它工具：26 个函数（查教材、建知识点、出题、排任务、删除等）以 JSON Schema 描述给模型，模型输出「我要调 create_questions、参数是…」，程序执行后把结果喂回，循环往复直到完成。
3. **约束层**——模型会跑偏，所以每个工具都套了笼子：**写入预算**（单对话知识点 ≤6 批、题目 ≤4 批、任务 ≤5 条）、删除类工具必须先只读确认、跨课程写入一律拒绝、读取也有预算防通读空转。

### 模块怎么协作

以「学生让 AI 出 5 道第三章的题」为例，一次请求穿过所有模块：

```
浏览器(AiChat SSE)
  → Uvicorn 收流 → main.py 路由(/api/ai/chat)
  → ai_agent.py 状态机接管
      → ai_helper.py 调模型（主阶跃，挂了切智谱）
      → 模型要求查教材 → execute_tool('get_node_text')
          → main.py/qushi.py 读 syllabus_nodes.content
      → 模型要求出题 → execute_tool('create_questions')
          → 预算校验 → 写 questions 表（sqlite3 参数化 SQL）
      → 复习算法不影响出题，但复习任务走 srs.py 排期
  → SSE 逐条推回前端 → 前端渲染工具卡片 + 跳转链接
```

关键点：**main.py 不直接调模型**，AI 相关全部经 ai_agent 统一入口，预算、日志、工具白名单只在这一处实现——改一处，所有入口生效。

## 三、状态机的构建（核心设计）

AI 拿到工具后最大的风险不是「不会做」，而是「做完就宣布完成」。所以 Agent 不是简单的 while 循环，而是一台**显式状态机**：

```
        ┌──────────── 不达标(gap)，最多回流 2 次 ────────────┐
        ▼                                                    │
   [act 执行] ──── 工具调用轮次用尽/完成 ────▶ [review 审查] ──┤
                                                     │        │
                                              审查通过        │
                                                     ▼        │
                                              [finalize 收尾] ┘
```

三个状态的职责：

- **act**：模型自主调用工具查资料、写库，产生「草稿」；轮次上限 8、工具调用上限 20，防止无限循环。
- **review**：**另起一次独立模型调用当质检员**，输出 `{done, gap}`——判「做没做成」的不是干活的那个模型自己，防「自己夸自己」。不通过时把 gap 原文喂回 act 重做，**最多回流 2 次**（MAX_REVIEWS）防死循环。
- **finalize**：收尾总结，把结论写入 `user_memory` 形成学生画像（save_memory 工具）。

为什么这样设计：全流程是确定性的代码（`backend/app/ai_agent.py` 的状态转移逻辑），模型只在每个状态里被调用——**模型负责单步的智能，代码负责全局的秩序**。这让行为可测试（`scripts/probe_state_machine.py` 能打印完整迁移轨迹）、可兜底（任何状态异常都回落到安全退出）。

验证方式：11 个真实模型场景自动判分（agent_eval，当前 11/11）+ 离线三幕演示（`scripts/demo_state_machine.py`，不联网、零 token）。
